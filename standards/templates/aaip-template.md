# AAIP-XXXX — <title>

> Leave `aaip: XXXX` as-is. Editors assign the number on acceptance. Numbers 001 and 002 are reserved.

## Abstract

Two or three sentences. What this proposes, and what changes if it is adopted.

## Problem

State the problem without reference to any product that solves it. If the problem cannot be stated that way, the proposal is not ready.

Say who currently bears the cost of the problem, and why existing mechanisms do not address it.

## Proposal

The normative content. Use RFC 2119 / RFC 8174 keywords — MUST, MUST NOT, SHOULD, SHOULD NOT, MAY — and use them only for genuine requirements.

Where the proposal defines a data format, give the field list with types and whether each is required.

## Conformance

- What an implementer MUST do to claim conformance.
- What a **verifier other than the implementer** MUST be able to check independently.
- What, if anything, cannot be checked externally, and why.

## Security considerations

Threats this addresses. Explicitly: the adversary assumed, and what is out of that model.

## Privacy considerations

What the proposal causes to be recorded, retained, or disclosed, and about whom. Where evidence records carry personal data, say what minimisation is expected.
